# 사업보고서 정정요구 사전 점검기 (annual-report-precheck)

상장사 공시담당자가 사업보고서를 제출하기 전에, 금감원이 점검하는 항목 중 "채워져는 있지만 충분하지 않은" 곳을 근거와 함께 짚어주는 도구.

## 무엇을 하는가

- 초안의 점검 항목 섹션(자기주식, 소수주주권·의사록, 단일판매·공급계약 진행상황, 재무 일부)을 입력받음
- 항목별로 정정요구 받을 가능성을 플래그하고, 금감원 기준에 비춘 근거 한 줄과 정정 후 통과한 타사 문단 예시를 붙임
- 정답은 금감원이 실제로 지적한 기록(DART 정정신고 표지)이라 라벨링 작업 없음

## 왜 이 문제인가

- 금감원이 매년 5월 사업보고서를 점검하고 6월 미흡 회사에 정정을 요구함. 2025년분 점검: 재무 221사, 자기주식 123사, 소각현황 234사, 제재현황 83사, 중대재해 24사 (금감원 2026.06.30)
- 2025.06~08 [기재정정] 사업보고서 348건 중 표지를 파싱한 109건의 102건이 정정요구 관련
- 정정요구 사유의 55%는 "미흡·보완"(칸은 차 있는데 내용 부족), 23%만 "빈칸·누락". 빈칸은 규칙으로 잡히지만 내용 부족은 읽어야 앎

## 구조

```
초안 섹션 ──▶ [1] 규칙 필터 ──▶ [2] LLM 판정 ──▶ [3] 타사 통과 예시 검색 ──▶ 플래그 + 근거 + 예시
              빈칸·누락·첨부·길이     "충분한가" + 근거 한 줄    임베딩 검색 (RAG)
                                      (API 모델 → 로컬 7B)
```

모든 단계는 같은 정답(`data/labels/*.tsv`)에 대해 `eval/score.py`로 채점하고 `eval/results.csv`에 누적함.

## 폴더 구조

```
annual-report-precheck/
├── data/
│   ├── labels/        정답 TSV (정정신고 표지에서 추출). 깃에 포함
│   ├── sections/      정정 전 원본의 항목별 섹션 텍스트. 평가용만 포함
│   └── raw/           사업보고서 원문 ZIP/XML. 깃 제외, 드라이브에서 받음
├── docs/              문제정의, 평가 설계, 금감원 점검항목
├── scripts/           수집 (OpenDART → 표지 파싱 → labels TSV)
├── rules/             규칙 baseline
├── llm/               LLM 판정 프롬프트·실행
├── eval/              채점기, results.csv
└── demo/              Streamlit
```

## 설치

```bash
git clone https://github.com/hyemin-hub/annual-report-precheck.git
cd annual-report-precheck
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env     # OPENDART_API_KEY 입력
```

OpenDART 키: https://opendart.fss.or.kr → 인증키 신청 (이메일 인증, 5분). 일 20,000회.

## 실행

```bash
# 1. 라벨 수집 (기간 지정). 건당 0.7초 쉬며 돌아감. 348건이면 약 5분
python scripts/collect_labels.py --start 20250601 --end 20250831 --out data/labels/labels_2025_06-08.tsv

# 2. 정정 전·후 본문 채우기 (원본 사업보고서 + 정정신고서에서 해당 섹션 추출). 122행 기준 약 20분. 끊기면 다시 실행하면 이어서 함
python scripts/fill_before.py --labels data/labels/labels_2025_06-08.tsv --out data/labels/labels_2025_06-08_text.tsv --only-pos

# 3. 규칙 baseline. 2번 결과를 넣어야 실제 본문 기준 점수가 나옴 (라벨 표만 넣으면 근사치라고 표시됨)
python rules/baseline.py data/labels/labels_2025_06-08_text.tsv

# 4. 채점 (어떤 방법이든 pred.tsv만 내면 됨)
python eval/score.py --pred llm/pred.tsv --gold data/labels/labels_2025_06-08.tsv --method "규칙+LLM"
```

원문 ZIP은 드라이브 공유 폴더(링크 추후)에서 받아 `data/raw/`에 풀 것. 깃에 올리지 않음.

## 정답이 어디 있나

DART에서 [기재정정] 사업보고서를 열면 첫 장이 "정정신고(보고)" 표지이고, "3. 정정사항" 표가 이렇게 생겼음.

| 항목 | 정정요구ㆍ명령 관련 여부 | 정정사유 | 정정 전 | 정정 후 |
|---|---|---|---|---|
| VI. 이사회 등 회사의 기관에 관한 사항 3. 주주총회 등 | 여 | 금융감독원 2024년 사업보고서 점검결과에 따른 기재 정정 | ... | ... |
| VII. 주주에 관한 사항 1. 최대주주 현황 | 아니오 | 특수관계인 지분율 누락 | ... | ... |

둘째 열이 "이 정정이 금감원 요구 때문인가". **여 = 정답(positive)**, 부 = 회사 자진정정(negative). 항목 열이 어느 섹션인지 가리키고, 정정 전/후 열이 근거 채점에 쓰임.

직접 보는 법:
1. dart.fss.or.kr → 공시서류검색 → 공시통합검색
2. 검색구분 "보고서명", `사업보고서` 입력
3. 기간 지정 (금감원 통보 직후인 6~8월에 몰림)
4. **"최종보고서" 체크 해제** (안 끄면 정정본이 안 보임)
5. 정기공시 체크 → 검색
6. [기재정정] 붙은 건 클릭 → 첫 페이지 표 확인

## 점검 항목 기준

연도별로 바뀜. 상세는 `docs/금감원_점검항목.md`.

| 연도분 | 비재무 항목 | 정정 데이터 시기 |
|---|---|---|
| 2024년분 | 자기주식, 소수주주권, 단일판매·공급계약 | 2025.06~08 (현재 평가셋) |
| 2025년분 | 자기주식, 중대재해, 형사 제재, 행정 제재 | 2026.06~08 (예정) |

평가는 해당 연도 항목 기준으로만. 자기주식과 재무 13개는 공통.

## labels.tsv 형식

| 열 | 내용 |
|---|---|
| rcp_no | DART 접수번호 |
| corp_name | 회사명 |
| item | 표지 "항목" 열. 사업보고서 섹션 |
| req | 여 / 부 / 예 / 아니오. 여·예가 positive |
| reason | 표지 "정정사유" 열 |
| before / after | 표지 "정정 전 / 정정 후" 열 (근거 채점용) |

## 현재 성능

2024년분 사업보고서, 2025.06~08 정정 표본. positive 122행 중 정정 전 본문이 채워진 114행 기준 (`rules/rule_baseline.ipynb`)

| 항목 | 규칙 baseline recall |
|---|---|
| 공급계약 | 15/48 = 31% |
| 소수주주권 | 14/41 = 34% |
| 자기주식 | 6/20 = 30% |
| 재무 | 0/4 = 0% |
| 전체 | 35/114 = 31% |

정정 유형 분포 (정정 전후 길이로 분류, 114행): 부연 추가 39, 소폭 추가 31, 길이 유지(숫자·문구 교체) 22, 빈칸·한 줄 18, 줄어듦 4. 유형별 규칙 recall: 빈칸 100%, 소폭 추가 42%, 길이 유지 14%, 부연 추가 3%. 규칙은 빈칸 유형을 전부 잡고 나머지 "글은 있는데 내용 부족"은 거의 못 잡음 → 이 84%가 LLM 단계의 몫. 재무 0%는 숫자 불일치 유형이라 글자 수 규칙 대상이 아님 → 숫자 대조 단계로 분리.

갱신은 `eval/results.csv`에 한 줄씩.

## 작업 규칙

- 브랜치: `feat/이름-파트` (예: `feat/hm-eval`). `main` 직접 푸시 금지
- `main` 머지는 PR + 1명 승인. 승인자는 파트별 짝으로 고정 (데이터↔규칙·채점, LLM↔로컬 모델, 문서는 아무나). 짝이 바쁘면 다른 사람이 대신 가능
- 승인하는 사람이 보는 것: 코드 전체가 아니라 (1) 결과 한 줄이 `eval/results.csv`에 붙었는지 (2) 원문 ZIP·`.env`가 섞여 들어오지 않았는지
- 코드·프롬프트를 바꾼 PR은 `eval/results.csv`에 결과 한 줄 추가 (PR 템플릿에 칸 있음)
- 원문 ZIP, 모델 가중치, 임베딩 인덱스, `.env`는 커밋 금지 (`.gitignore`에 있음)
- 올리는 데이터는 `data/labels/*.tsv`(라벨 표)와 `eval/results.csv`뿐. 원문 ZIP은 공개 자료라 올려도 되지만 용량(한 해분 수백 MB, GitHub 파일당 100MB 제한) 때문에 드라이브에 둠

## 알려진 한계

- 선택 편향: "여" 라벨은 금감원이 본 회사에서만 나옴. negative에 미흡인데 안 걸린 것이 섞여 오탐이 과대평가됨. recall은 영향 없음
- 라벨 노이즈: 표지 서식이 회사마다 달라 152건 중 43건 파싱 실패. 30건 수작업 대조 예정
- 점검 항목이 매년 바뀜. 연도별 평가셋 분리
- 사업보고서는 연 1회. 분기·반기보고서, 증권신고서(같은 표지 구조)로 확장 가능
