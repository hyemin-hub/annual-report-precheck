# rules/ 규칙 baseline

## 무엇을 하는가
AI 없이 규칙 세 개(비었나 / "해당사항 없음"인가 / 섹션별 최소 글자 수보다 짧나)만으로 "금감원이 지적할 섹션"을 찍어보고, 실제 지적된 것 중 몇 %를 맞혔는지(recall) 잰다. 이 숫자가 이후 모든 단계(API, 로컬 모델)가 넘어야 할 기준.

## 파일
- `rule_baseline.ipynb`: 코랩에서 위부터 순서대로 실행. 데이터 받기부터 recall까지 한 파일
- `baseline.py`: 같은 규칙의 스크립트 버전. `python rules/baseline.py data/labels/labels_2025_06-08_text.tsv`

## 노트북 단계
| 단계 | 하는 일 | 걸리는 시간 | 결과 |
|---|---|---|---|
| 1 | 깃허브에서 라벨 표(122행) 읽기 | 즉시 | 화면에 표 5행 |
| 2 | OpenDART API로 정정 전·후 보고서 원문을 받아 해당 섹션만 잘라 `before`/`after` 열에 넣기 | 전체 10분 | `labels_text.tsv`, 원문은 `dart_xml/` |
| 3 | 규칙으로 `before` 판정 → 항목별 recall | 즉시 | 화면 출력 |
| 4 | 규칙이 놓친 행 3개의 정정 전·후 본문 | 즉시 | 화면 출력 |
| 5 | `eval/results.csv`에 붙일 한 줄 | 즉시 | 화면 출력 |
| 6 | 정정 전후 길이로 지적 유형 분포 | 즉시 | 화면 출력 |

## 2단계 status 읽는 법
- `ok_sub`: 소제목(가·나·다)까지 정확히 잘라냄
- `ok`: 번호 섹션(예: "4. 주식의 총수 등") 전체. 소제목 표기가 회사마다 달라 못 자른 경우
- `ok_top`: 큰 섹션(예: "VI.")만 찾음. 너무 넓어 글자 수 규칙이 잘 안 걸림
- `no_orig`: 원본 사업보고서를 못 찾음 → 그 행은 recall 계산에서 빠짐
- `no_section`: 항목 번호를 원문에서 못 찾음 → 라벨 표의 항목 표기가 특이한 경우, 손으로 확인

## 3단계 출력 읽는 법
```
본문 채워진 104행 기준 규칙 recall
  공급계약: 15/47 = 32%     ← 공급계약 지적 47건 중 규칙이 15건 찍음
  전체: 32/104 = 31%
```
recall만 있고 오탐(정상 보고서를 잘못 찍는 비율)은 아직 없음. 오탐은 정정 없는 보고서를 모아야 잴 수 있어 다음 단계.

## 규칙을 바꿔보려면
3단계 셀의 `EMPTY`(빈칸 판정 정규식)와 `MIN_CHARS`(섹션별 최소 글자 수)만 고치고 3단계부터 다시 실행. 2단계는 다시 안 해도 됨. 바꾼 뒤 recall이 오르면 5단계 한 줄을 `eval/results.csv`에 추가하고 PR.

## 주의
- 첫 셀의 `KEY`에 OpenDART 인증키를 넣고 실행하되, 깃허브에 올릴 땐 `KEY = ""`로 비울 것
- 코랩 런타임이 끊기면 `dart_xml/`과 `labels_text.tsv`가 지워짐. 전체 실행 후 `labels_text.tsv`는 내려받아 둘 것
